# Architecture of the TypeScript SDK

This page is for contributors. It covers what each module of `src/` holds, which way
imports may point, how a call and a verification flow through the code, and where a
common change goes. The layer table below is the one `tests/architecture.test.ts`
enforces. Change both together.

The SDK has no runtime dependencies (Node.js built-ins only) and one package entry,
`src/index.ts`, which defines `GenesisMeshClient` and re-exports every public name.

## Layers

Imports point down the table or stay inside a layer. They never point up.

| Rank | Layer | Modules |
|---|---|---|
| 1 | leaf | `types.ts`, `errors.ts`, `strict-json.ts`, `auth.ts`, `metadata.ts`, `canonical-registry.ts` |
| 2 | protocol | `canonical.ts`, `strict.ts`, `validation.ts`, `execution.ts`, `data_intent.ts`, `out-of-band.ts`, `remediation.ts`, `grants.ts`, `key-history.ts`, `anchors.ts`, `verify.ts`, `audit-pack.ts`, `outbox.ts` |
| 3 | transport | `client.ts`, and one sub-client per NA route group: `agreement.ts`, `attestation.ts`, `boundary.ts`, `consensus.ts`, `data_usage.ts`, `disclosure.ts`, `evidence.ts`, `health.ts`, `network_authority.ts`, `policy.ts`, `grants-client.ts`, `evidence_store.ts` |
| 4 | orchestration | `governance.ts`, `grant-holder.ts` |
| 5 | entry | `index.ts` |

The architecture test checks every `import` and `export … from` in `src/`, type-only
ones included. It enforces four rules:

- **No upward imports.** A module imports from its own layer or a lower one. The test
  allows one exception in `ALLOWED_UPWARD_IMPORTS`: `canonical-registry.ts -> strict.ts`
  (type-only). The list can only shrink. The test fails on a new upward import, and on
  a listed import that has gone until you delete its line.
- **No runtime import cycles.** A cycle made only of type-only imports is allowed.
- **Every `src/` file has a layer.** A new file fails the test until you add it to
  `LAYERS`.
- **Only `src/` modules and `node:` built-ins are imported.**

Within the layers, three more rules hold. Nothing tests them, so review them:

- **No HTTP below transport.** The protocol layer never calls `fetch` or
  `HttpTransport`.
- **Sub-clients send parameters, not signed models.** A sub-client may call protocol
  code, for example `evidence_store.ts` verifies what it reads and flushes the outboxes,
  but it holds no crypto primitives.
- **`auth.ts` stays minimal.** It holds canonical JSON, Ed25519 signing and admin
  headers, and nothing more.

## Modules

| Module | What it holds |
|---|---|

| `validation.ts` | Shape checks of complete signed wire artifacts, and timestamp parsing. |
| `execution.ts` | `ExecutionRecorder`: builds and signs execution evidence. |
| `data_intent.ts` | Builds and signs agent-side data access intents. |

| `audit-pack.ts` | Audit packs and archives, verified offline from files (1.5.0). |
| `outbox.ts` | The evidence and record outboxes, in memory and as files. |

## How a call flows

**An NA call.** The flow is
`gm.<sub-client>.<method>(params)` → `HttpTransport` (`client.ts`) →
`fetch(baseUrl + path)`:

- The transport builds the path. IDs travel as encoded path segments, and the query goes
  through `buildPath`.
- For admin routes, `auth.ts` signs the request headers.
- The transport applies the timeout. When retries are configured, it retries an
  idempotent request on a network error or a 429, 502, 503 or 504.
- With several `baseUrls`, an idempotent request moves to the next instance on a
  transport failure or a 502, 503 or 504. A non-idempotent request moves only when the
  connection failed.
- It reads the body with `decodeUtf8` and `parseJson`. An error status becomes a typed
  error through `fromHttpError`.

**A governed action.** `governedAction` (`governance.ts`) runs these steps:

1. It asks the NA for a decision through `gm.boundary.evaluate`.
2. It verifies the decision offline with `verifyBoundaryDecision` (`verify.ts`).
3. It runs the caller's action.
4. `ExecutionRecorder` (`execution.ts`) signs the evidence, after the metadata guard
   (`metadata.ts`).
5. It submits the evidence through `gm.evidenceStore`. When the NA cannot be reached, it
   queues the evidence in the outbox (`outbox.ts`) and flushes it later in order.

**Offline verification.** There are two entry points:

- **An evidence export.** `parseExportLines` → `verifyEvidenceEvents` (`verify.ts`). The
  verifier checks each entry against strict JSON, the registry (`strict.ts`), its shape
  (`validation.ts`), its canonical form (`canonical.ts`), the NA's key history
  (`key-history.ts`) and its kind's rules (`out-of-band.ts`, `remediation.ts`,
  `grants.ts`), then checks the hash chains.
- **An audit pack.** `verifyAuditPack` (`audit-pack.ts`) runs the same checks over the
  pack's files, and checks them against the store anchors (`anchors.ts`).

## Where a change goes

Each recipe lists the files to touch and the check that fails if one is missed. Every
change also needs a changelog fragment (`changelog.d/<version>/<name>.md`).

### A record kind verified offline

1. **Vectors and registry.** Copy the core's `field_registry.json` and the kind's suite
   into `tests/fixtures/conformance/`, then run `npm run sync:registry`. This regenerates
   `canonical-registry.ts`, including `ENTRY_KINDS`, so `EntryKind` gains the kind.
   *Check:* `tests/field_registry.test.ts` fails when the registry is stale.
2. **Wire interfaces.** Add the record interface and its reason or code unions to
   `types.ts`.
3. **Shape check.** Add a `validX` shape check to `validation.ts`. If the record can be
   quarantined, also add the kind to the `record_kind` lists in `validation.ts` and
   `out-of-band.ts`.
4. **Verifier.** In `verify.ts`, add the `case` in `verifyEvidenceEvents` and an entry in
   each of `PAYLOAD_CHECKS`, `RECORD_ID`, `ENVELOPE_FIELDS`, `OUT_OF_BAND_MODELS` and
   `KEY_ROLES` where it applies, plus its `check*Entry` function. *Check:* `tsc` fails
   when the switch or a `Record<EntryKind, …>` table misses the kind
   (`tests/kind-tables.test.ts` proves this).
5. **Outbox.** If clients submit the kind, add it to `RECORD_OUTBOX_KINDS` and to the ID
   detection in `outbox.ts`, and to the kind unions and the flush order in
   `evidence_store.ts`.
6. **Audit pack.** Add the kind's change-record mapping to `audit-pack.ts`.
7. **Exports.** Export the new names from `index.ts`, then run `npm run api:update`.
   *Check:* `npm run api:check` fails until the API report is updated.
8. **Tests.** Add a `tests/<kind>-conformance.test.ts` over the suite, plus unit tests.
   Add an `e2e.test.ts` block, which fails under `GM_E2E_REQUIRED=1` when the NA lacks
   the feature, and the feature switch in `scripts/e2e_na.py`.
9. **Docs.** Update the guide in `docs/` and the README.

### A client method for an NA route

1. Add the method to the route group's sub-client, or to a new one in the transport
   layer. Add a new sub-client file to `LAYERS` and as a field of `GenesisMeshClient`.
2. Add the request and response interfaces to `types.ts`, and export them from
   `index.ts`.
3. Add a row to the route table in `tests/sdk-routes.test.ts`, which checks the method,
   path, admin signing and body. Add method tests in `tests/<domain>.test.ts`.
4. Run `npm run api:update` and commit the API report.
5. Update the README section of the sub-client.

*Checks:* the route table, `npm run api:check`, and the architecture test if the method
imports from the wrong layer.

### An error or reason code

1. Add the code to its union in `types.ts` (or in `strict-json.ts`, `grants.ts`, …).
2. Map it in `errors.ts`, or add it to a refusal set (`PERMANENT_REFUSALS` and
   `RECORD_PERMANENT_REFUSALS` in `outbox.ts`, `QUARANTINED_USE_CODES` in `grants.ts`).
3. Add a test that the NA's response produces it.

*Checks:* `tsc` refuses a `fail(seq, '<code>')` whose code is not in the union. Nothing
yet compares the unions with the core's error codes.

### A conformance suite or vector update

1. Copy the core's files into `tests/fixtures/conformance/` unchanged, then run
   `npm run sync:registry`.
2. For a TypeScript-only fixture, use `scripts/generate_vectors.py`.

*Checks:* the suite's `*-conformance.test.ts`, and `tests/field_registry.test.ts` for
the registry. The core's interop workflow compares the copies byte for byte.

### Holder or outbox behaviour

1. Change `grant-holder.ts`, `outbox.ts`, and the flush in `evidence_store.ts`.
2. Test it in `tests/grant-holder.test.ts`, `tests/record-outbox.test.ts` or
   `tests/outbox.test.ts`, and in the grants end-to-end scenario (`npm run test:e2e`).

### A new module

1. Put shared code in the lowest layer that can hold it, and list the file in `LAYERS`
   in `tests/architecture.test.ts`.
2. If it is public, export it from `index.ts` and update the API report.

*Check:* the architecture test.

## Ratchets

These checks only tighten. Raise a floor when coverage rises, and remove an allowlist
line when its import goes.

**Layer rule.** The test is `tests/architecture.test.ts`, run by `npm test`.

**Public API report.**

- `etc/genesis-mesh-sdk.api.md` is generated by API Extractor from the built
  declarations.
- To update it, run `npm run build` and then `npm run api:update`.
- `npm run api:check` fails in CI when the report is stale. Review the diff of the
  report like code.

**API compatibility.**

- The workflow "API compatibility" (`scripts/api-compat.mjs`) compares the report with
  the latest release tag.
- An incompatible change fails unless the pull request carries the `breaking` label and
  adds a fragment with an `### Upgrading` section. Incompatible changes are removed or
  changed exports and members, and new required members of input types.
- A release made before the report existed is compared through
  `etc/baseline/<tag>.api.md`. Delete the file once a newer release carries the report.

**Coverage floors.**

- `npm run test:coverage` runs the suite with the floors in `jest.config.cjs`.
- The critical files have their own floors: `verify.ts`, `audit-pack.ts`, `grants.ts`,
  `strict-json.ts` and `canonical.ts`.
- The other `src/` files share a global floor.

**Property tests.**

- `tests/properties.test.ts` uses fast-check on strict JSON, the canonical form and the
  path segments.
- `GM_PROPERTY_RUNS` sets the number of cases (default 200).
- A failure prints the seed to replay it.
